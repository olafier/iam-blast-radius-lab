How does IAM permission scope affect the blast radius of a compromised cloud identity?

Three test identities — Policy A narrow, Policy B moderate, Policy C broad — each run the same fixed set of 100 AWS actions across 12 services. The only variable is IAM permission scope; blast radius is the share of those actions the identity can actually perform.

Blast radius per identity

Simple count vs impact-weighted

ASR counts every successful action equally. WBR weights each by category (read 1 · write 2 · destroy 3 · escalate 4), so an identity that can only read scores lower than its raw count suggests.

Fixed action set × identity

Every row is one of the 100 actions attempted by all three identities, grouped by service. AWS decides Allow or Deny; nothing else changes between columns. Notice that Policy C's only denials are IAM identity-mutation actions — a broad PowerUser role still cannot escalate its own privileges.

How the numbers are computed

Metric A — Action Success Rate

Share of attempted actions the identity completed.

ASR = successful ÷ attempted × 100
Metric B — Impact-Weighted Blast Radius

Same ratio, but each action carries the weight of its category. Weights were fixed before any run.

WBR = Σ w(successful) ÷ Σ w(attempted) × 100
